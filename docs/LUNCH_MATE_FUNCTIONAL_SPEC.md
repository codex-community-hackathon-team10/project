## 0. 문서 목적

이 문서는 대학생의 수업 시간표와 선호 점심 시간을 이용해 공강이 겹치는 점심 메이트를 추천하고, 만남 제안부터 약속 확정까지 연결하는 서비스의 기능 요구사항을 정의한다.

각 기능은 다음 형식으로 기술한다.

- 기능 ID 및 기능명
- 설명
- 액터
- 사전 조건
- 기능 흐름
- 수용 기준
- 예외 처리

## 1. 서비스 범위와 원칙

### 1.1 MVP 목표

사용자가 다음 핵심 경로를 처음부터 끝까지 수행할 수 있어야 한다.

```text
데모 계정 로그인
→ 프로필과 학교 설정
→ 시간표 등록
→ 공강 자동 계산
→ 원하는 점심 시간과 관심 활동 설정
→ 점심 메이트 추천 확인
→ 공통 시간 기반 장소 3개 추천
→ 만남 제안
→ 상대방 수락
→ 약속 확인
```

### 1.2 MVP 범위

#### 필수 구현

- 사전 생성된 자체 로그인 데모 계정
- 학교·캠퍼스·최소 프로필 설정
- 주간 수업 시간표 전체 저장
- 점심 시간대의 공강 자동 계산
- 선호 만남 시간과 최소 만남 시간 설정
- 관심 활동 및 관심사 설정
- 공통 공강 기반 사용자 추천
- 추천 이유 표시
- 검증된 캠퍼스 장소 데이터 기반 장소 3개 추천
- 만남 제안·수락
- `ACCEPTED` 제안 기반 약속 조회
- 최소 사용자 차단 생성 및 매칭 제외
- 공통 공강 외 상세 시간표 비공개

#### 선택 구현

- 공개 회원가입·Refresh Token·학교 이메일 인증
- 개별 수업 CRUD
- 제안 거절·취소
- 생성형 AI 추천 문구와 템플릿 폴백
- 관심 표시
- 차단 목록·해제 및 신고 UI

#### MVP 제외

- 그룹 매칭
- 학교 간 매칭
- 실시간 채팅
- 푸시 알림
- 공휴일·휴강·보강 예외 일정
- 전체 대학·캠퍼스 데이터 구축
- 정교한 ML 추천 모델

### 1.3 기본 정책

| 항목 | MVP 정책 |
|---|---|
| 인증 방식 | 자체 로그인, P0는 사전 생성된 데모 계정만 사용 |

| 약속 | 상태가 `ACCEPTED`인 만남 제안. 별도 Appointment 엔티티는 만들지 않음 |

# 2. Auth

## 목적

이메일과 비밀번호를 이용한 자체 사용자 인증을 제공한다. 이 장은 회원가입, 로그인, 세션 유지, 로그아웃, 사용자 정보 조회를 다룬다.

## FR-AUTH-001 회원가입 `[P1]`

### 설명

비회원 사용자는 이메일과 비밀번호로 계정을 생성할 수 있어야 한다. 회원가입 성공 직후 로그인 상태가 되며 프로필 설정 화면으로 이동한다.

### 액터

비회원 사용자

### 사전 조건

- 사용자가 서비스에 가입하지 않은 이메일을 보유하고 있다.
- 사용자가 이용약관 및 개인정보 처리방침에 동의한다.

### 기능 흐름

1. 사용자가 회원가입 화면에서 이메일, 비밀번호, 비밀번호 확인을 입력한다.
2. 클라이언트가 입력 형식을 검증한다.
3. 서버가 이메일 중복 여부와 입력값을 다시 검증한다.
4. 서버가 비밀번호를 단방향 해시로 변환해 계정을 생성한다.
5. 서버가 Access Token과 Refresh Token을 발급한다.
6. 사용자를 최초 프로필 설정 화면으로 이동시킨다.

### 수용 기준

- 이메일은 앞뒤 공백 제거 및 소문자 정규화 후 저장한다.
- 이메일 형식이 유효해야 한다.
- 비밀번호는 8자 이상이며 영문과 숫자를 각각 1자 이상 포함해야 한다.
- 비밀번호와 비밀번호 확인 값이 같아야 한다.
- 동일 이메일로 계정이 중복 생성되지 않는다.
- 비밀번호 원문은 데이터베이스와 로그에 저장되지 않는다.
- 회원가입 성공 시 Access Token과 Refresh Token이 발급된다.
- 신규 사용자의 프로필 상태는 `INCOMPLETE`로 생성된다.

### 예외 처리

- 이미 가입된 이메일인 경우: `이미 사용 중인 이메일입니다.`를 표시한다.
- 입력 형식이 잘못된 경우: 해당 필드 아래에 원인을 표시한다.
- 서버 오류로 계정 생성에 실패한 경우: 계정이 일부만 생성되지 않도록 전체 처리를 롤백하고 재시도 안내를 표시한다.

## FR-AUTH-002 로그인 `[P0]`

### 설명

가입 사용자는 이메일과 비밀번호로 로그인할 수 있어야 한다. P0는 팀이 사전 생성한 2~3개의 `DEMO_VERIFIED` 계정만 사용한다.

### 액터

로그아웃 상태의 가입 사용자

### 사전 조건

사용자 계정이 존재하며 차단 또는 탈퇴 상태가 아니다.

### 기능 흐름

1. 사용자가 이메일과 비밀번호를 입력한다.
2. 서버가 정규화한 이메일로 계정을 조회한다.
3. 서버가 저장된 비밀번호 해시와 입력 비밀번호를 비교한다.
4. 인증 성공 시 Access Token과 Refresh Token을 발급한다.
5. 프로필이 완료된 사용자는 추천 화면으로 이동한다.
6. 프로필이 완료되지 않은 사용자는 프로필 설정 화면으로 이동한다.

### 수용 기준

- 올바른 자격 증명으로 로그인할 수 있다.
- 잘못된 이메일 또는 비밀번호에는 동일한 실패 메시지를 사용한다.
- 로그인 성공 후 인증이 필요한 API를 호출할 수 있다.
- 프로필 완료 여부에 따라 이동 화면이 구분된다.
- `UNVERIFIED` 사용자는 프로필을 편집할 수 있지만 매칭·제안 화면에는 접근할 수 없다.

### 예외 처리

- 이메일 또는 비밀번호가 일치하지 않는 경우: `이메일 또는 비밀번호를 확인해 주세요.`를 표시한다.
- 탈퇴 또는 이용 제한 계정인 경우: 로그인하지 않고 해당 상태에 맞는 안내를 표시한다.
- 서버 통신 실패 시: 입력한 비밀번호를 보존하지 않고 재시도 안내를 표시한다.

## FR-AUTH-003 세션 유지 및 토큰 갱신 `[P1]`

### 설명

로그인 사용자는 Access Token 만료 시 유효한 Refresh Token으로 세션을 갱신할 수 있어야 한다.

### 액터

로그인 사용자, 클라이언트 애플리케이션

### 사전 조건

유효하고 만료되지 않은 Refresh Token이 존재한다.

### 기능 흐름

1. 클라이언트가 인증 API에서 Access Token 만료 응답을 받는다.
2. 클라이언트가 토큰 갱신 API를 1회 호출한다.
3. 서버가 Refresh Token의 유효성, 만료, 폐기 여부를 확인한다.
4. 유효한 경우 새 Access Token을 발급한다.
5. 클라이언트가 실패했던 요청을 1회 재시도한다.

### 수용 기준

- 유효한 Refresh Token으로 새 Access Token이 발급된다.
- 만료 또는 폐기된 Refresh Token으로는 갱신할 수 없다.
- 여러 요청이 동시에 만료되어도 무한 갱신 또는 무한 재시도가 발생하지 않는다.
- 토큰에 비밀번호 등 민감한 정보가 포함되지 않는다.

### 예외 처리

- 토큰 갱신 실패 시: 로컬 인증 상태를 제거하고 로그인 화면으로 이동한다.
- 네트워크 오류 시: 자동 재시도를 반복하지 않고 로그인 필요 상태를 안내한다.

## FR-AUTH-004 로그아웃 `[P1]`

### 설명

로그인 사용자는 현재 기기에서 로그아웃할 수 있어야 한다.

### 액터

로그인 사용자

### 사전 조건

사용자가 로그인 상태다.

### 기능 흐름

1. 사용자가 로그아웃을 선택한다.
2. 서버가 현재 Refresh Token을 폐기한다.
3. 클라이언트가 저장한 인증 정보를 제거한다.
4. 로그인 화면으로 이동한다.

### 수용 기준

- 로그아웃 후 기존 Refresh Token으로 세션을 갱신할 수 없다.
- 로그아웃 후 인증이 필요한 화면에 접근하면 로그인 화면으로 이동한다.
- 서버 로그아웃 요청이 실패하더라도 클라이언트의 인증 정보는 제거된다.

### 예외 처리

- 서버 통신 실패 시: 로컬 로그아웃을 완료하고 서버 토큰 폐기 실패를 기록한다.

## FR-AUTH-005 내 사용자 정보 조회 `[P0]`

### 설명

로그인 사용자는 현재 계정과 프로필의 요약 정보를 조회할 수 있어야 한다.

### 액터

로그인 사용자

### 사전 조건

유효한 인증 정보가 있다.

### 기능 흐름

1. 클라이언트가 내 정보 API를 호출한다.
2. 서버가 인증된 사용자 ID로 계정과 프로필을 조회한다.
3. 서버가 이메일, 닉네임, 프로필 완료 여부, 학교·캠퍼스 정보를 반환한다.

### 수용 기준

- 사용자는 자신의 정보만 조회할 수 있다.
- 비밀번호 해시와 토큰 정보는 응답에 포함되지 않는다.
- 프로필이 미완성인 경우 누락 항목을 판단할 수 있는 상태값을 반환한다.

### 예외 처리

- 인증 정보가 유효하지 않으면 `401 Unauthorized`를 반환한다.
- 계정을 찾을 수 없으면 인증 정보를 폐기하고 다시 로그인하도록 안내한다.

# 3. Profile

## 목적

매칭에 필요한 학교, 캠퍼스, 기본 정보, 활동 목적과 관심사를 등록하고 관리한다.

## FR-PROFILE-001 최초 프로필 설정

### 설명

신규 사용자는 추천 기능을 이용하기 전에 필수 프로필을 등록해야 한다.

### 액터

프로필 미완성 로그인 사용자

### 사전 조건

사용자가 로그인 상태이며 프로필 상태가 `INCOMPLETE`다.

### 기능 흐름

1. 사용자가 학교를 선택한다.
2. 선택한 학교에 속한 캠퍼스를 선택한다.
3. 학과, 학년, 학생 유형, 닉네임을 입력한다.
4. 선택적으로 프로필 이미지와 자기소개를 입력한다.
5. 서버가 필수 입력값과 닉네임 정책을 검증한다.
6. 프로필을 저장하고 상태를 `COMPLETE`로 변경한다.
7. 시간표 등록 화면으로 이동한다.

### 수용 기준

- 학교, 캠퍼스, 학과, 학년, 학생 유형, 닉네임은 필수다.
- 학년은 `1`, `2`, `3`, `4`, `OTHER` 중 하나다.
- 학생 유형은 `DOMESTIC`, `INTERNATIONAL`, `EXCHANGE`, `OTHER` 중 하나다.
- 닉네임은 2~20자이며 서비스 내 금칙어를 포함할 수 없다.
- 캠퍼스는 선택한 학교에 소속된 값이어야 한다.
- 프로필 저장 완료 전에는 추천 화면을 이용할 수 없다.

### 예외 처리

- 학교와 캠퍼스 관계가 올바르지 않으면 저장하지 않고 다시 선택하도록 안내한다.
- 닉네임이 이미 사용 중이면 다른 닉네임 입력을 요청한다.
- 이미지 업로드 실패 시: 이미지 없이 나머지 프로필을 저장할 수 있다.

## FR-PROFILE-002 관심 활동 및 관심사 설정

### 설명

사용자는 함께하고 싶은 활동과 관심사를 복수 선택할 수 있어야 한다.

### 액터

프로필을 보유한 로그인 사용자

### 사전 조건

기본 프로필이 저장되어 있다.

### 기능 흐름

1. 사용자가 활동 목록에서 원하는 항목을 선택한다.
2. 사용자가 관심사 목록에서 원하는 항목을 선택한다.
3. 언어교환을 선택한 경우 사용 가능 언어와 연습 희망 언어를 선택한다.
4. 서버가 선택값을 검증하고 저장한다.

### 수용 기준

- 활동은 `LUNCH`, `CAFE`, `STUDY`, `LANGUAGE_EXCHANGE`, `EXERCISE`, `HOBBY`, `CAMPUS_TOUR`, `MAKE_FRIENDS` 중 복수 선택할 수 있다.
- MVP 추천을 위해 활동을 최소 1개 선택해야 하며 기본 선택은 `LUNCH`다.
- 관심사는 허용된 목록에서 최대 10개 선택할 수 있다.
- 동일 항목이 중복 저장되지 않는다.
- 언어교환을 선택하지 않은 사용자에게 언어 입력은 필수가 아니다.

### 예외 처리

- 허용되지 않은 활동 또는 관심사 값은 저장하지 않고 `400 Bad Request`를 반환한다.
- 선택 한도를 초과하면 초과한 항목을 저장하지 않고 안내한다.

## FR-PROFILE-003 프로필 조회 및 수정

### 설명

사용자는 자신의 프로필을 조회하고 수정할 수 있어야 한다.

### 액터

로그인 사용자

### 사전 조건

프로필이 존재한다.

### 기능 흐름

1. 사용자가 내 프로필 화면을 연다.
2. 서버가 현재 프로필을 반환한다.
3. 사용자가 수정할 항목을 변경하고 저장한다.
4. 서버가 입력값을 검증한 뒤 변경 내용을 저장한다.

### 수용 기준

- 프로필 필수 항목을 빈 값으로 수정할 수 없다.
- 수정 결과가 이후 추천에 반영된다.
- 학교 또는 캠퍼스 변경 시 기존 추천 결과는 무효화하고 다시 계산한다.
- 변경하지 않은 필드는 유지된다.

### 예외 처리

- 존재하지 않는 학교·캠퍼스로 수정할 수 없다.
- 동시 수정 충돌 시 최신 정보를 다시 불러오도록 안내한다.

# 4. Schedule

## 목적

사용자의 주간 수업 시간표를 등록하고 점심 시간대의 공강을 계산한다.

## FR-SCHEDULE-001 주간 수업 전체 저장 `[P0]`

### 설명

사용자는 요일, 과목명, 시작 시간, 종료 시간, 강의실로 구성된 주간 수업 목록을 한 번에 저장할 수 있어야 한다. 서버는 기존 목록을 전체 교체한다.

### 액터

로그인 사용자

### 사전 조건

기본 프로필 설정이 완료되어 있다.

### 기능 흐름

1. 사용자가 화면에서 수업 항목을 추가·수정·삭제한다.
2. 각 항목에 요일, 과목명, 시작·종료 시간과 선택 강의실을 입력한다.
3. 클라이언트가 전체 목록의 형식과 중복을 검증한다.
4. 서버가 전체 목록을 다시 검증한다.
5. 서버가 하나의 트랜잭션으로 기존 주간 시간표를 전체 교체한다.
6. 저장된 시간표를 기준으로 공강을 다시 계산한다.

### 수용 기준

- 요일은 월요일부터 금요일까지만 선택할 수 있다.
- 과목명, 시작 시간, 종료 시간은 필수이며 강의실은 선택이다.
- 시간은 30분 단위로 입력한다.
- 시작 시간은 종료 시간보다 빨라야 한다.
- 같은 요일에 시간이 겹치는 수업은 저장할 수 없다.
- 빈 목록은 전체 시간표 삭제를 의미한다.
- 한 항목이라도 잘못되면 일부만 저장하지 않는다.
- 저장 성공 후 시간표와 공강 계산 결과가 즉시 갱신된다.

### 예외 처리

- 기존 수업과 겹치면 겹치는 수업을 표시하고 저장하지 않는다.
- 잘못된 시간 형식이나 범위가 입력되면 해당 필드에 오류를 표시한다.
- 저장 실패 시 입력값을 유지하고 재시도할 수 있게 한다.

## FR-SCHEDULE-002 개별 수업 수정 및 삭제 `[P1]`

### 설명

사용자는 자신이 등록한 수업의 정보를 수정하거나 삭제할 수 있어야 한다.

### 액터

로그인 사용자

### 사전 조건

수정 또는 삭제할 수업이 존재한다.

### 기능 흐름

1. 사용자가 시간표에서 수업을 선택한다.
2. 수정하는 경우 필드를 변경하고 저장한다.
3. 삭제하는 경우 삭제 확인 후 수업을 제거한다.
4. 서버가 변경된 시간표를 저장한다.
5. 공강과 추천 결과를 다시 계산한다.

### 수용 기준

- 사용자는 자신의 수업만 수정하거나 삭제할 수 있다.
- 수정 시 FR-SCHEDULE-001과 동일한 검증 규칙을 적용한다.
- 삭제는 사용자의 확인 후 실행한다.
- 변경 후 공강, 추천 후보, 기존 미확정 제안 가능 여부가 갱신된다.
- 이미 확정된 약속은 시간표 변경만으로 자동 취소되지 않는다.

### 예외 처리

- 존재하지 않거나 다른 사용자의 수업에 접근하면 `404 Not Found`를 반환한다.
- 변경으로 기존 대기 중 제안 시간과 충돌하면 사용자에게 경고를 표시한다.

## FR-SCHEDULE-003 공강 자동 계산

### 설명

서버는 사용자의 시간표를 바탕으로 평일 점심 서비스 시간 내 공강을 자동 계산해야 한다.

### 액터

시스템, 로그인 사용자

### 사전 조건

사용자의 주간 시간표가 저장되어 있다.

### 기능 흐름

1. 서버가 요일별 수업 시간을 시작 시간순으로 정렬한다.
2. 서비스 시간인 11:00~15:00과 각 수업 구간의 겹침을 계산한다.
3. 서비스 시간에서 수업 구간을 제외해 공강 구간을 생성한다.
4. 30분 미만의 구간은 제거한다.
5. 요일별 공강 시작·종료 시간과 길이를 반환한다.

### 수용 기준

- 공강 계산은 서버 기준으로 일관되게 수행한다.
- 수업의 시작·종료 경계는 겹치지 않는 것으로 처리한다. 예: 수업이 12:00에 끝나면 공강은 12:00부터 시작할 수 있다.
- 겹치거나 인접한 수업 구간은 계산 전에 병합한다.
- 수업이 없는 요일은 11:00~15:00 전체를 공강으로 계산한다.
- 서비스 시간 밖의 수업은 점심 공강 계산에 영향을 주지 않는다.
- 결과에는 요일, 시작 시간, 종료 시간, 총 분이 포함된다.

### 예외 처리

- 유효하지 않은 수업 데이터가 발견되면 잘못된 데이터를 조용히 무시하지 않고 계산 실패를 기록한다.
- 시간표가 비어 있는 경우: `수업이 없는 시간표`임을 명시하고 전체 서비스 시간을 공강으로 표시한다.

## FR-SCHEDULE-004 시간표 이미지 OCR 등록 `[선택]`

### 설명

사용자는 시간표 이미지를 업로드해 수업 후보를 자동 추출할 수 있다. OCR 결과는 사용자의 확인 없이 저장하지 않는다.

### 액터

로그인 사용자

### 사전 조건

지원 형식의 시간표 이미지가 있다.

### 기능 흐름

1. 사용자가 이미지 파일을 업로드한다.
2. 서버가 파일 형식과 크기를 검증한다.
3. OCR 서비스가 요일, 과목명, 시작·종료 시간, 강의실 후보를 추출한다.
4. 사용자에게 추출 결과와 인식 실패 항목을 보여준다.
5. 사용자가 항목을 수정·삭제·확정한다.
6. 확정한 항목만 수업으로 저장한다.
7. 공강을 다시 계산한다.

### 수용 기준

- 지원 형식은 JPG, PNG이며 최대 크기는 10MB다.
- OCR 결과는 `임시` 상태로 생성되며 확정 전 추천에 사용되지 않는다.
- 사용자가 모든 추출 필드를 수정할 수 있다.
- 기존 수업과 겹치는 항목은 확정 전에 표시한다.
- OCR 실패 여부와 관계없이 직접 입력으로 전환할 수 있다.

### 예외 처리

- 지원하지 않는 파일 또는 용량 초과 시 업로드를 거부하고 원인을 표시한다.
- OCR 서비스 장애 또는 시간 초과 시 직접 입력을 안내한다.
- 인식 결과가 없으면 빈 시간표로 저장하지 않는다.

# 5. Availability

## 목적

시간표상 공강과 실제 만남 의사를 분리하기 위해 선호 점심 시간과 최소 만남 시간을 관리한다.

## FR-AVAILABILITY-001 선호 만남 시간 설정

### 설명

사용자는 평일 중 실제로 점심 메이트를 만나고 싶은 시간대를 복수 등록할 수 있어야 한다.

### 액터

로그인 사용자

### 사전 조건

기본 프로필이 완료되어 있다.

### 기능 흐름

1. 사용자가 요일을 선택한다.
2. 11:00~15:00 내에서 시작·종료 시간을 선택한다.
3. 필요하면 다른 요일 또는 같은 요일의 다른 시간대를 추가한다.
4. 최소 만남 시간을 선택한다.
5. 서버가 시간 중복과 범위를 검증해 저장한다.
6. 공강과 선호 시간의 교집합인 유효 가능 시간을 계산한다.

### 수용 기준

- 선호 시간은 월요일부터 금요일까지 설정할 수 있다.
- 시작·종료 시간은 30분 단위다.
- 같은 요일의 겹치거나 인접한 구간은 하나로 병합한다.
- 최소 만남 시간은 30분, 60분, 90분, 120분 중 선택한다.
- 기본 최소 만남 시간은 60분이다.
- 선호 시간은 공강과 겹치는 구간만 매칭에 사용한다.
- 설정 변경 후 추천 결과가 다시 계산된다.

### 예외 처리

- 시작 시간이 종료 시간보다 늦거나 같으면 저장하지 않는다.
- 서비스 시간 밖의 입력은 저장하지 않는다.
- 공강과 겹치는 선호 시간이 하나도 없으면 이유와 수정 방법을 안내한다.

# 6. Matching

## 목적

동일 학교·캠퍼스 사용자 중 공강과 선호 점심 시간이 겹치는 상대를 찾아 추천하고, 추천 근거를 투명하게 제공한다.

## FR-MATCH-001 추천 후보 계산

### 설명

시스템은 사용자의 조건에 맞는 점심 메이트 후보를 계산하고 적합도 순으로 제공해야 한다.

### 액터

로그인 사용자, 시스템

### 사전 조건

- 프로필 설정이 완료되어 있다.
- 시간표가 등록되어 있다.
- 선호 만남 시간과 활동이 설정되어 있다.

### 기능 흐름

1. 서버가 요청 사용자의 유효 가능 시간을 계산한다.
2. 동일 학교·동일 캠퍼스의 활성 사용자를 후보로 조회한다.
3. 자기 자신, 미인증 사용자, 차단 관계 사용자, 이미 넘긴 사용자를 제외한다.
4. 두 사용자의 유효 가능 시간 교집합을 계산한다.
5. 양쪽 사용자의 최소 만남 시간을 모두 충족하지 못한 후보를 제외한다.
6. 공통 시간, 활동, 관심사, 언어 조건으로 점수를 계산한다.
7. 점수 내림차순으로 정렬해 추천 목록을 반환한다.

### 수용 기준

- 자기 자신은 추천되지 않는다.
- 다른 학교 또는 캠퍼스 사용자는 MVP에서 추천되지 않는다.
- `DEMO_VERIFIED` 또는 `SCHOOL_EMAIL_VERIFIED` 사용자만 추천된다.
- 양쪽 최소 만남 시간 중 더 긴 값을 공통 시간 기준으로 사용한다.
- 공통 가능 시간이 없는 사용자는 추천되지 않는다.
- 차단한 사용자와 나를 차단한 사용자는 서로 추천되지 않는다.
- 정확한 수업명, 강의실, 전체 시간표는 매칭 응답에 포함되지 않는다.
- 동일 조건에서는 결과 순서가 예측 가능하도록 동일한 점수 규칙을 사용한다.

### 예외 처리

- 추천 후보가 없으면 빈 목록과 함께 `선호 시간을 넓히거나 최소 만남 시간을 줄여보세요.`를 표시한다.
- 시간표 또는 선호 시간이 없으면 추천을 실행하지 않고 누락된 설정 화면으로 안내한다.
- 추천 계산 실패 시 마지막 결과를 성공 결과처럼 표시하지 않고 재시도 상태를 보여준다.

## FR-MATCH-002 매칭 점수 계산

### 설명

시스템은 설명 가능한 규칙 기반 점수를 사용해 추천 순서를 결정한다.

### 액터

시스템

### 사전 조건

후보가 필수 필터 조건을 통과했다.

### 기능 흐름

1. 가장 긴 공통 가능 시간의 길이를 계산한다.
2. 공통 활동 개수를 계산한다.
3. 공통 관심사 개수를 계산한다.
4. 언어교환 수요가 서로 맞는지 계산한다.
5. 항목별 점수를 합산한다.
6. 총점과 근거 항목을 저장 또는 응답한다.

### 수용 기준

MVP 점수는 다음 규칙을 사용한다.

| 항목 | 점수 |
|---|---:|
| 공통 가능 시간 | 30분당 10점, 최대 60점 |
| `LUNCH` 활동 일치 | 20점 |
| 그 외 공통 활동 | 항목당 5점, 최대 15점 |
| 공통 관심사 | 항목당 3점, 최대 15점 |
| 언어교환 조건 상호 일치 | 10점 |

- 총점이 같은 경우 가장 긴 공통 가능 시간, 공통 관심사 수, 최근 활동 시각 순으로 정렬한다.
- 점수 계산에 성별, 국적 등 명세에 없는 민감 정보를 사용하지 않는다.
- 점수와 추천 이유의 근거 데이터가 일치해야 한다.

### 예외 처리

- 선택 정보가 없는 항목은 0점으로 계산하며 오류로 처리하지 않는다.
- 점수 계산 규칙 버전이 바뀌면 결과 재현을 위해 버전을 함께 관리한다.

## FR-MATCH-003 추천 카드 조회

### 설명

사용자는 추천 상대의 최소 프로필과 공통 가능 시간, 추천 이유를 카드 형태로 확인할 수 있어야 한다.

### 액터

로그인 사용자

### 사전 조건

추천 후보가 1명 이상 존재한다.

### 기능 흐름

1. 사용자가 추천 화면을 연다.
2. 서버가 추천 순서대로 후보 카드를 반환한다.
3. 사용자가 카드에서 상대의 공개 정보와 추천 이유를 확인한다.
4. 사용자가 관심 표시, 만나기 제안 또는 넘기기를 선택한다.

### 수용 기준

- 카드에는 닉네임, 프로필 이미지, 학년과 같은 캠퍼스 여부만 표시한다.
- 카드에는 가장 가까운 공통 가능 요일·시간, 공통 활동, 공통 관심사, 추천 이유를 표시한다.
- 학과, 학생 유형, 자기소개는 기본 추천 카드에 표시하지 않는다.
- 이메일, 연락처, 수업명, 강의실, 전체 시간표와 상대의 개별 선호 시간은 표시하지 않는다.
- 공통 시간이 여러 개인 경우 최대 3개까지만 표시한다.

### 예외 처리

- 상대가 비활성화되거나 차단된 경우 카드를 노출하지 않고 다음 후보를 보여준다.
- 프로필 이미지가 없거나 로드에 실패하면 기본 이미지를 사용한다.

## FR-MATCH-004 관심 표시 및 넘기기 `[선택]`

### 설명

사용자는 추천 상대에게 관심을 표시하거나 현재 추천에서 제외할 수 있어야 한다.

### 액터

로그인 사용자

### 사전 조건

추천 카드가 노출되어 있다.

### 기능 흐름

1. 사용자가 `관심` 또는 `넘기기`를 선택한다.
2. 서버가 사용자와 대상, 액션, 시각을 저장한다.
3. 넘기기를 선택하면 해당 카드를 목록에서 제거한다.
4. 서로 관심을 표시한 경우 상호 관심 상태를 보여준다.

### 수용 기준

- 같은 상대에 대한 동일 액션은 중복 생성되지 않는다.
- 넘긴 상대는 MVP 기간 동안 다시 추천하지 않는다.
- 관심 표시는 상대방의 연락처나 전체 프로필 접근 권한을 부여하지 않는다.

### 예외 처리

- 존재하지 않거나 비활성 상대에게 액션을 저장할 수 없다.
- 저장 실패 시 UI에서 성공한 것처럼 제거하지 않고 재시도할 수 있게 한다.

## FR-MATCH-005 AI 추천 이유 생성 `[선택]`

### 설명

생성형 AI는 규칙 기반 매칭 결과를 자연스러운 한두 문장으로 설명한다. AI는 추천 후보와 점수를 결정하지 않는다.

### 액터

시스템

### 사전 조건

규칙 기반 추천 후보와 추천 근거가 계산되어 있다.

### 기능 흐름

1. 서버가 닉네임을 제외한 최소 추천 근거를 구조화한다.
2. AI에 공통 시간, 활동, 관심사 데이터만 전달한다.
3. AI가 추천 이유 문장을 생성한다.
4. 서버가 응답 형식과 금지 정보 포함 여부를 검증한다.
5. 유효한 문구를 추천 카드에 표시한다.

### 수용 기준

- AI 입력에 이메일, 연락처, 전체 시간표, 수업명, 강의실을 포함하지 않는다.
- AI 문구는 계산된 사실만 사용하며 새로운 사실을 만들지 않는다.
- 결과는 최대 2문장으로 제한한다.
- AI 호출 실패 여부와 관계없이 추천 목록을 제공한다.
- 폴백 문구는 템플릿으로 생성한다. 예: `월요일 12:00~13:30에 공강이 겹치고, 두 분 모두 점심 활동을 선호해요.`

### 예외 처리

- AI 호출 실패 또는 시간 초과 시 템플릿 추천 이유를 사용한다.
- 응답에 근거 없는 정보 또는 개인정보가 포함되면 폐기하고 템플릿을 사용한다.

# 7. Place Recommendation

## 목적

공통 점심 시간, 캠퍼스, 활동과 선택 조건을 이용해 실제 후보 데이터 안에서 만남 장소를 추천한다. AI는 장소를 선택하거나 장소 정보를 생성하지 않고 추천 이유 문구만 작성한다.

## FR-PLACE-001 공통 시간 기반 장소 추천 `[P0]`

### 설명

사용자가 만남 제안을 준비할 때 시스템은 선택한 캠퍼스·날짜·시간·활동을 기준으로 주변 장소를 최대 3개 추천한다.

### 액터

만남을 제안하는 로그인 사용자

### 사전 조건

- 두 사용자 사이에 제안 가능한 공통 시간이 있다.
- 캠퍼스에 검증된 장소 데이터가 등록되어 있다.

### 기능 흐름

1. 사용자가 날짜, 시작·종료 시간과 활동을 선택한다.
2. 선택적으로 예산과 분위기를 선택한다.
3. 서버가 캠퍼스의 검증된 장소 6~10개를 조회한다.
4. 활동, 예산, 분위기, 도보 시간과 만남 길이로 후보 점수를 계산한다.
5. 상위 장소를 최대 3개 반환한다.
6. AI가 각 장소의 계산된 근거만 이용해 추천 이유를 생성한다.
7. 사용자는 추천 장소를 선택하거나 장소명을 직접 입력한다.

### 수용 기준

- 점심 활동이면 식당을 우선 추천한다.
- 만남 시간이 60분 이하이면 도보 시간이 짧고 빠른 식사가 가능한 장소를 우선한다.
- 응답은 최대 3개다.
- 장소명, 거리, 가격대와 영업 정보는 저장된 데이터에서만 가져온다.
- LLM이 존재하지 않는 장소나 속성을 생성할 수 없다.
- AI 호출 실패 시 `공강이 60분이라 캠퍼스에서 도보 3분 거리의 빠른 식사 장소를 추천해요.` 형식의 템플릿을 사용한다.
- 사용자는 추천 장소 없이 직접 장소를 입력해 제안을 완료할 수 있다.

### 예외 처리

- 장소 후보가 없거나 추천 계산에 실패하면 빈 추천 목록과 직접 입력 가능 상태를 반환한다.
- AI 호출 실패는 장소 추천 API 전체 실패로 처리하지 않는다.
- 장소 데이터의 영업시간이 미확인이면 영업 중이라고 표시하지 않는다.

# 8. Proposal

## 목적

추천 상대에게 구체적인 점심 만남을 제안하고, 상대가 수락 또는 거절하도록 한다.

## FR-PROPOSAL-001 만남 제안 생성

### 설명

사용자는 추천 상대에게 날짜, 시간, 활동, 장소를 포함한 만남 제안을 보낼 수 있어야 한다.

### 액터

로그인 사용자

### 사전 조건

- 상대가 활성 사용자이며 차단 관계가 아니다.
- 두 사용자 사이에 제안 가능한 공통 시간이 존재한다.

### 기능 흐름

1. 사용자가 추천 카드에서 `만나기 제안`을 선택한다.
2. 시스템이 가장 가까운 공통 가능 날짜와 시간 후보를 표시한다.
3. 시스템이 조건에 맞는 장소를 최대 3개 추천한다.
4. 사용자가 추천 장소를 선택하거나 장소명을 직접 입력한다.
5. 서버가 두 사용자의 공통 가능 시간, 확정 제안 충돌과 입력값을 검증한다.
6. 상태가 `PENDING`인 제안을 생성한다.
7. 상대방의 받은 제안 목록에 노출한다.

### 수용 기준

- 날짜, 시작 시간, 종료 시간, 활동과 추천 또는 직접 입력 장소는 필수다.
- 제안 시간은 30분 단위이며 미래 시각이어야 한다.
- 제안 날짜의 요일이 두 사용자의 주간 공통 가능 요일과 일치해야 한다.
- 제안 시간은 두 사용자의 공통 가능 시간 안에 포함되어야 한다.
- 두 사용자 모두 같은 날짜의 `ACCEPTED` 제안과 시간이 겹치지 않아야 한다.
- 추천 장소 선택 시 장소 snapshot을 저장하고, 직접 입력 장소는 2~50자다.
- 메시지는 최대 200자다.
- 동일한 두 사용자·날짜·시간의 대기 중 제안은 중복 생성되지 않는다.
- 생성 직후 상태는 `PENDING`이다.
- P0는 공휴일·휴강을 판단하지 않고 해당 날짜 요일의 주간 규칙을 적용한다.

### 예외 처리

- 공통 가능 시간이 변경된 경우: 최신 가능 시간을 다시 보여주고 제안을 생성하지 않는다.
- 둘 중 한 명에게 겹치는 `ACCEPTED` 제안이 있으면 충돌 약속을 노출하지 않고 생성을 거부한다.
- 상대가 탈퇴·차단 상태인 경우: 제안을 생성하지 않는다.
- 입력 중 제안 시간이 지나간 경우: 새로운 시간 선택을 요청한다.

## FR-PROPOSAL-002 받은 제안 수락 및 거절

### 설명

제안을 받은 사용자는 대기 중인 제안을 수락하거나 거절할 수 있어야 한다.

### 액터

제안 수신자

### 사전 조건

제안 상태가 `PENDING`이며 현재 사용자가 수신자다.

### 기능 흐름

1. 사용자가 받은 제안 상세를 확인한다.
2. 사용자가 `수락` 또는 `거절`을 선택한다.
3. 수락 시 서버가 공통 가능 시간, 제안 시작 시각과 양쪽 사용자의 `ACCEPTED` 제안 충돌을 다시 확인한다.
4. 수락하면 상태를 `ACCEPTED`, 거절하면 `REJECTED`로 변경한다.
5. 수락된 제안으로 약속 정보를 제공한다.

### 수용 기준

- 제안 수신자만 수락 또는 거절할 수 있다.
- 하나의 제안은 최초 1회만 응답할 수 있다.
- 수락 성공 시 별도 Appointment를 생성하지 않고 이 제안이 양쪽 약속 탭에 표시된다.
- 거절 시 상대방에게 거절 사유나 추가 개인정보를 요구하지 않는다.
- 상태 변경 시 처리 시각을 기록한다.

### 예외 처리

- 이미 처리되거나 취소된 제안은 다시 응답할 수 없다.
- 수락 직전 일정 충돌이 확인되면 수락하지 않고 충돌 사실을 안내한다.
- 수락 시각에 공통 가능 시간이 사라졌으면 수락하지 않는다.
- 제안 시작 시각이 지났으면 `CANCELED`로 변경하고 `TIME_EXPIRED`를 기록한다.
- 동시에 수락 요청이 발생해도 상태 변경은 1회만 성공한다.

## FR-PROPOSAL-003 만남 제안 취소

### 설명

발신자는 대기 중 제안을 취소할 수 있고, 수락된 제안은 양쪽 참여자 중 누구나 취소할 수 있어야 한다.

### 액터

제안 발신자

### 사전 조건

제안 상태가 `PENDING` 또는 `ACCEPTED`이며 현재 사용자가 참여자다.

### 기능 흐름

1. 사용자가 보낸 제안 상세에서 `제안 취소`를 선택한다.
2. 사용자에게 취소 확인을 요청한다.
3. 서버가 상태를 `CANCELED`로 변경한다.
4. 양쪽 제안 목록에 취소 상태를 표시한다.

### 수용 기준

- `PENDING` 제안은 발신자만 취소할 수 있다.
- `ACCEPTED` 제안은 양쪽 참여자 모두 취소할 수 있다.
- 취소된 제안은 수락 또는 거절할 수 없다.
- 취소 기록은 상태와 처리 시각을 보존한다.

### 예외 처리

- 이미 거절·취소됐거나 종료 시각이 지난 제안은 취소할 수 없다.
- 상태가 동시에 변경된 경우 최신 상태를 반환하고 중복 처리하지 않는다.

# 9. Appointment View

## 목적

별도 Appointment 엔티티 없이 상태가 `ACCEPTED`인 `MeetingProposal`을 약속 탭에 표시한다. 제안이 날짜·시간·장소·참여자·상태의 단일 원본이다.

## FR-APPOINTMENT-001 수락된 제안 조회 `[P0]`

### 설명

사용자는 자신이 발신자 또는 수신자인 `ACCEPTED` 제안을 예정 약속으로 조회할 수 있어야 한다.

### 액터

로그인 사용자

### 기능 흐름

1. 사용자가 약속 탭을 연다.
2. 서버가 사용자가 참여한 `ACCEPTED` 제안을 날짜·시간순으로 조회한다.
3. 화면이 상대 닉네임, 날짜·시간, 활동, 장소와 상태를 표시한다.

### 수용 기준

- 제안 수락 시 별도 Appointment 레코드를 생성하지 않는다.
- 약속 ID 대신 Proposal ID를 사용한다.
- 예정 약속은 시작 시각 오름차순, 지난 약속은 시작 시각 내림차순으로 표시한다.
- 상대의 이메일, 연락처와 전체 시간표는 수락 후에도 공개하지 않는다.
- 확정 약속 취소는 `FR-PROPOSAL-003`의 동일 제안 상태를 `CANCELED`로 변경한다.

### 예외 처리

- `ACCEPTED` 제안이 없으면 빈 약속 화면을 표시한다.
- 다른 사용자가 참여한 제안은 조회할 수 없다.

# 9. Safety & Privacy

## 목적

모르는 사람과 실제로 만나는 서비스에 필요한 최소 안전 기능과 정보 공개 원칙을 제공한다.

## FR-SAFETY-001 사용자 차단 `[P0 최소 구현]`

### 설명

사용자는 원하지 않는 상대를 차단할 수 있어야 한다.

### 액터

로그인 사용자

### 사전 조건

차단 대상 사용자가 존재한다.

### 기능 흐름

1. 사용자가 상대 프로필 또는 제안 화면에서 차단을 선택한다.
2. 시스템이 차단의 영향을 안내하고 확인을 요청한다.
3. 서버가 차단 관계를 저장한다.
4. 양쪽 사용자를 서로의 추천과 신규 제안 대상에서 제외한다.

### 수용 기준

- 자기 자신을 차단할 수 없다.
- 같은 대상에 대한 차단은 중복 생성되지 않는다.
- 차단 관계는 상대에게 직접 알리지 않는다.
- 차단 후 양쪽은 서로에게 신규 제안을 보낼 수 없다.
- 기존 확정 약속은 자동 취소하지 않고 별도로 취소하도록 안내한다.
- P0는 차단 생성과 매칭 제외만 구현하며 차단 목록·해제 UI는 P1이다.

### 예외 처리

- 존재하지 않는 사용자는 차단할 수 없다.
- 차단 저장 실패 시 성공 상태로 표시하지 않는다.

## FR-SAFETY-002 사용자 신고 `[선택]`

### 설명

사용자는 부적절한 프로필이나 행동을 운영자에게 신고할 수 있어야 한다.

### 액터

로그인 사용자

### 사전 조건

신고 대상 사용자가 존재한다.

### 기능 흐름

1. 사용자가 상대 프로필 또는 약속 화면에서 신고를 선택한다.
2. 신고 유형과 선택적 상세 내용을 입력한다.
3. 서버가 신고자, 대상, 유형, 내용, 관련 화면, 시각을 저장한다.
4. 사용자에게 접수 완료를 알리고 차단 여부를 추가로 묻는다.

### 수용 기준

- 신고 유형은 `INAPPROPRIATE_PROFILE`, `HARASSMENT`, `SPAM`, `NO_SHOW`, `OTHER` 중 하나다.
- 상세 내용은 최대 500자다.
- 신고 내용은 신고 대상에게 공개하지 않는다.
- 신고만으로 상대 계정을 자동 정지하지 않는다.
- 운영자가 처리할 수 있도록 상태를 `RECEIVED`로 저장한다.

### 예외 처리

- 자기 자신을 신고할 수 없다.
- 동일 사용자가 같은 대상을 반복 신고하는 경우 중복 여부를 운영 로그에 표시한다.

## FR-PRIVACY-001 시간표 정보 최소 공개

### 설명

서비스는 매칭과 약속에 필요한 공통 가능 시간만 상대에게 공개해야 한다.

### 액터

시스템, 모든 사용자

### 사전 조건

사용자가 시간표를 등록했다.

### 기능 흐름

1. 사용자가 자신의 수업 정보를 등록한다.
2. 서버가 수업 정보를 공강 계산에만 사용한다.
3. 추천 응답을 생성할 때 공통 가능 시간만 추출한다.
4. 상대에게 수업 상세를 제외한 공통 가능 시간을 반환한다.

### 수용 기준

- 추천·제안·약속 API에 상대의 과목명과 강의실을 포함하지 않는다.
- 상대의 개별 공강 전체 목록을 공개하지 않는다.
- 화면에는 두 사용자에게 공통인 구간만 표시한다.
- 사용자는 자신의 시간표만 조회·수정·삭제할 수 있다.
- 로그에 시간표 전체나 인증 정보를 불필요하게 기록하지 않는다.

### 예외 처리

- 권한 없는 사용자가 다른 사용자의 시간표 API에 접근하면 `403 Forbidden` 또는 `404 Not Found`를 반환한다.
- 응답 변환 실패 시 원본 시간표를 폴백 응답으로 반환하지 않는다.

# 10. 공통 상태 및 비기능 요구사항

## 10.1 상태 정의

### 사용자 프로필 상태

| 상태 | 설명 |
|---|---|
| `INCOMPLETE` | 필수 프로필 설정 전 |
| `COMPLETE` | 추천 기능 이용 가능 |

### 만남 제안 및 약속 상태

| 상태 | 설명 | 가능한 다음 상태 |
|---|---|---|
| `PENDING` | 상대 응답 대기 | `ACCEPTED`, `REJECTED`, `CANCELED` |
| `ACCEPTED` | 상대가 수락한 확정 약속 | `CANCELED` |
| `REJECTED` | 상대가 거절 | 없음 |
| `CANCELED` | 발신자 또는 약속 참여자가 취소 | 없음 |

## 10.2 공통 오류 응답

모든 API 오류는 최소한 다음 필드를 가진 일관된 형식으로 반환한다.

```json
{
  "code": "VALIDATION_ERROR",
  "message": "입력값을 확인해 주세요.",
  "fieldErrors": [
    {
      "field": "startTime",
      "reason": "종료 시간보다 빨라야 합니다."
    }
  ]
}
```

- 사용자에게 보여줄 메시지와 디버깅용 내부 로그를 분리한다.
- 서버 오류를 빈 성공 응답으로 변환하지 않는다.
- 외부 서비스 오류는 핵심 기능의 폴백 가능 여부를 함께 정의한다.

## 10.3 보안 요구사항

- 비밀번호는 검증된 비밀번호 해시 알고리즘으로 저장한다.
- API 키, 토큰, 데이터베이스 비밀번호는 환경변수로 관리한다.
- `.env` 파일은 Git에 커밋하지 않는다.
- 인증이 필요한 모든 API에서 서버가 사용자 권한을 검증한다.
- 로그인 실패 응답으로 계정 존재 여부를 노출하지 않는다.
- 외부 입력은 서버 경계에서 스키마 검증한다.
- 사용자 작성 문자열은 출력 시 안전하게 처리해 XSS를 방지한다.
- 민감한 토큰과 비밀번호를 애플리케이션 로그에 남기지 않는다.

## 10.4 성능 및 안정성 요구사항

- 일반 조회 API는 데모 환경에서 2초 이내 응답을 목표로 한다.
- 추천 API는 후보 100명 기준 3초 이내 응답을 목표로 한다.
- 중복 요청으로 회원, 제안, 약속이 중복 생성되지 않아야 한다.
- AI와 OCR이 실패해도 수동 시간표 등록과 규칙 기반 추천은 동작해야 한다.
- 모든 날짜·시간 저장은 타임존이 명확한 형식을 사용하고 화면에는 KST로 표시한다.

## 10.5 접근성 및 사용성 요구사항

- 아이콘만 있는 버튼에는 텍스트 레이블 또는 접근성 이름을 제공한다.
- 색상만으로 제안 상태나 오류를 구분하지 않는다.
- 입력 오류는 오류 발생 필드 가까이에 원인을 표시한다.
- 주요 데모 경로는 모바일 화면 폭에서도 완료할 수 있어야 한다.

# 11. MVP 데모 시나리오

## 시나리오 A — 추천부터 약속 확정까지

### 준비 데이터

- 사용자 A: 연세대학교 신촌캠퍼스, 월요일 12:00~14:00 유효, 점심·언어교환 선호
- 사용자 B: 연세대학교 신촌캠퍼스, 월요일 12:00~13:30 유효, 점심·언어교환 선호
- 사용자 C: 다른 캠퍼스 또는 공통 시간 없음
- 검증된 신촌 캠퍼스 식당·카페 6~10개

### 데모 흐름

1. 사용자 A가 자체 로그인한다.
2. 사용자 A의 시간표에서 월요일 12:00~14:00 공강을 확인한다.
3. 선호 시간 월요일 12:00~14:00, 최소 60분을 확인한다.
4. 추천 화면에서 사용자 B를 확인한다.
5. 추천 이유 `월요일 12:00~13:30에 90분 동안 공강이 겹치고, 두 분 모두 점심과 언어교환을 선호해요.`를 확인한다.
6. 월요일 12:00~13:00을 선택하고 가까운 장소 추천 3개와 추천 이유를 확인한다.
7. 추천 장소 하나를 선택해 만남을 제안한다.
8. 사용자 B로 로그인해 제안을 수락한다.
9. 양쪽 약속 화면에서 `ACCEPTED` 제안을 확인한다.

### 데모 합격 조건

- 사용자 B는 추천되고 사용자 C는 추천되지 않는다.
- 상대의 과목명, 강의실, 전체 시간표가 한 번도 노출되지 않는다.
- AI 호출을 끊어도 템플릿 추천 이유가 표시된다.
- 장소 추천 실패 시 직접 장소 입력으로 제안할 수 있다.
- 제안 수락 후 별도 Appointment 없이 양쪽 계정에서 같은 `ACCEPTED` 제안을 확인할 수 있다.
- 같은 날짜·시간의 확정 제안이 있으면 생성 또는 수락이 거부된다.

## 시나리오 B — 후보 없음과 복구

1. 최소 만남 시간을 120분으로 설정한다.
2. 후보 없음 안내를 확인한다.
3. 안내에 따라 최소 만남 시간을 60분으로 변경한다.
4. 추천 후보가 다시 나타나는지 확인한다.
