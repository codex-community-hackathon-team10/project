# 공강 기반 점심 메이트 & 장소 추천 서비스 기능 명세서

> 문서 버전: v0.2  
> 작성 기준: 2026-08-16 KST  
> 핵심 카피: **시간표의 빈칸을, 새로운 만남으로 채워보세요.**  
> MVP 포지셔닝: **공강이 겹치는 캠퍼스 점심 메이트를 찾고, AI가 두 사람에게 맞는 캠퍼스 주변 장소까지 제안하는 서비스**

---

## 1. 목표와 범위

### 1.1 해결하려는 문제

학생들은 공강이 있어도 누구와 언제, 어디서 점심을 먹을지 정하기 어렵다. 이 서비스는 같은 캠퍼스 학생 중 실제로 만날 수 있는 점심 공강이 겹치는 사람을 추천하고, 공강 길이와 활동 목적에 맞는 장소를 제안한다.

### 1.2 핵심 사용자 흐름

```text
로그인
→ 학교·프로필 설정
→ 점심 시간표 등록
→ 실제 만남 가능 시간 설정
→ 공통 공강 점심 메이트 추천
→ 공통 시간에 맞는 장소 추천
→ 날짜·시간·장소를 선택해 제안
→ 상대 수락
→ 확정 약속 확인
```

### 1.3 MVP 범위

#### P0 — 데모 필수

- 데모 계정 로그인 또는 인증 서비스 기반 로그인
- 하나의 사전 등록 학교·캠퍼스 선택
- 기본 프로필, 관심사, 점심 활동 설정
- 월~금 11:00~15:00 수업 직접 입력·수정·삭제
- 공강 및 실제 만남 가능 시간 계산
- 동일 캠퍼스 내 공통 가능 시간 기반 추천
- 추천 이유 표시
- 공통 시간·활동에 맞는 장소 3개 추천
- 장소를 포함한 만남 제안, 수락·거절·취소
- 확정 약속 조회
- 상대에게 공통 가능 시간만 공개

#### P1 — 시간이 남으면

- 관심 표시와 넘기기
- 차단 및 신고
- 프로필 이미지·자기소개
- 카페·스터디·언어교환 등 점심 외 만남 및 장소 추천
- 실제 장소 검색 API 연동

#### MVP 제외

- 자체 Access/Refresh Token 구현 및 다기기 세션 관리
- 시간표 이미지 OCR
- 실시간 채팅, 푸시 알림, 그룹 매칭
- 학교 간 매칭
- 공휴일·휴강·시험기간 등 날짜별 시간표 예외
- 실시간 영업 여부·좌석 수 보장
- 정교한 ML 추천 모델

### 1.4 데모 운영 전제

- 학교·캠퍼스 데이터는 데모 대상 캠퍼스만 사전 등록한다.
- 데모용 사용자 3명 이상을 사전 생성한다.
- 학생 인증은 정식 서비스 확장 항목이다. MVP는 초대/데모 계정을 대상으로 한다.
- 인증은 Supabase Auth, Clerk 등 검증된 인증 서비스를 우선 사용한다. 자체 인증을 구현한다면 비밀번호 원문 저장 금지, 해시 저장, HTTP-only Secure 쿠키 등 별도 보안 설계가 필요하다.

## 2. 공통 정책과 용어

| 항목 | MVP 정책 |
|---|---|
| 서비스 대상 시간 | 평일 11:00~15:00 KST |
| 시간 단위 | 30분 |
| 시간표 | 매주 반복되는 요일 기반 수업 시간표 |
| 최소 만남 시간 | 기본 60분, 30/60/90/120분 중 선택 |
| 추천 범위 | 동일 학교·동일 캠퍼스, 발견 허용 상태인 사용자 |
| 기본 활동 | `LUNCH` 필수. 다른 활동은 공통 관심 태그 및 추천 보조 조건으로만 사용 |
| 장소 데이터 | 캠퍼스 주변 사전 검수 장소 데이터 |
| 개인정보 | 상대의 전체 시간표, 수업명, 강의실, 이메일, 연락처를 공개하지 않음 |

| 용어 | 정의 |
|---|---|
| 공강 | 서비스 시간 중 수업과 겹치지 않는 구간 |
| 선호 시간 | 사용자가 실제로 만나고 싶다고 설정한 구간 |
| 유효 가능 시간 | `공강 ∩ 선호 시간` |
| 공통 가능 시간 | 두 사용자의 유효 가능 시간 교집합 |
| 제안 가능 시간 | 공통 가능 시간이면서 양쪽의 확정 약속과 겹치지 않는 특정 날짜·시간 |
| 장소 후보 | 활동·캠퍼스·공강 길이 조건을 통과한 사전 등록 장소 |

### 2.1 날짜와 시간 정책

- 시간표와 선호 시간은 요일별 반복 규칙이다.
- 만남 제안은 미래의 특정 날짜와 시작·종료 시각을 가진다.
- 서버는 제안 날짜의 요일에 해당하는 공통 가능 시간 안인지 검증한다.
- 서버는 두 사용자의 `ACCEPTED` 약속과 시간이 겹치면 제안을 생성·수락할 수 없게 한다.
- 공휴일과 휴강은 MVP에서 반영하지 않는다. 화면에 `정규 수업일 기준`이라고 안내한다.

## 3. 화면과 기능 요구사항

## FR-AUTH-001 로그인

**설명**: 사용자는 데모 계정 또는 외부 인증 서비스로 로그인한다.

**수용 기준**

- 로그인한 사용자만 프로필, 시간표, 추천, 제안 화면에 접근한다.
- 프로필 미완성 사용자는 온보딩으로 이동한다.
- 인증 실패 시 비밀번호나 계정 존재 여부를 노출하지 않는 안내를 표시한다.
- 데모에서는 사용자 A/B/C 계정을 빠르게 전환할 수 있다.

## FR-PROFILE-001 프로필 및 매칭 조건 설정

**입력값**

| 항목 | 필수 | 규칙 |
|---|---:|---|
| 학교·캠퍼스 | O | 사전 등록된 관계만 선택 |
| 닉네임 | O | 2~20자 |
| 학과·학년 | O | 카드에는 학년 또는 공개 동의 정보만 기본 노출 |
| 학생 유형 | O | 재학생/유학생/교환학생/기타 |
| 점심 활동 | O | `LUNCH` 기본 선택 |
| 관심사 | O | 최대 10개 |
| 언어 | X | 언어교환 선택 시에만 입력 |

**수용 기준**

- 필수값이 저장되기 전에는 추천을 조회할 수 없다.
- 학교 또는 캠퍼스를 바꾸면 추천 결과를 다시 계산한다.
- 같은 캠퍼스 사용자의 초기 카드에는 닉네임, 학년, 활동, 관심사, 공통 시간만 표시한다.
- 학과·학생 유형·자기소개는 공개 설정 또는 상세 화면에서만 노출한다.

## FR-PREFERENCE-001 매칭 선호 설정

**설명**: 사용자는 매칭 노출 여부와 최소 만남 시간을 설정한다. 이 값은 요일별 선호 시간과 분리된 사용자 전체 설정이다.

| 항목 | 기본값 | 규칙 |
|---|---|---|
| 발견 허용 | 허용 | 비허용 시 다른 사용자 추천 대상에서 제외 |
| 최소 만남 시간 | 60분 | 30/60/90/120분 중 하나 |

**수용 기준**

- 설정을 바꾸면 추천 후보와 정렬 결과를 다시 계산한다.
- 최소 만남 시간은 개별 선호 시간 구간이 아니라 사용자 단위로 하나만 저장한다.
- 발견 허용을 끄면 내 추천 화면은 이용할 수 있지만 다른 사용자에게는 추천되지 않는다.

## FR-SCHEDULE-001 수업 시간표 관리

**설명**: 사용자는 점심 시간대 수업을 요일별로 직접 등록·수정·삭제한다.

**입력값**: 요일, 과목명, 시작 시각, 종료 시각, 강의실(선택)

**수용 기준**

- 요일은 월~금, 시각은 30분 단위로 입력한다.
- 시작 시각은 종료 시각보다 빨라야 한다.
- 같은 요일의 수업 구간은 서로 겹칠 수 없다.
- 저장·수정·삭제 직후 공강과 추천 결과를 다시 계산한다.
- 과목명과 강의실은 본인 시간표에서만 조회 가능하다.

## FR-SCHEDULE-002 공강 계산

**설명**: 서버는 11:00~15:00에서 수업 구간을 제외한 공강을 계산한다.

**계산 규칙**

1. 요일별 수업을 시작 시각 순으로 정렬하고, 겹치거나 인접한 구간을 병합한다.
2. 서비스 시간과 겹치는 수업만 반영한다.
3. 서비스 시간에서 병합된 수업 구간을 뺀 결과를 공강으로 반환한다.
4. 30분 미만 공강은 제거한다.

**수용 기준**

- 수업이 12:00에 끝나면 공강은 12:00부터 시작할 수 있다.
- 수업이 없는 요일은 11:00~15:00 전체가 공강이다.
- 서비스 시간 밖 수업은 점심 공강 계산에 영향을 주지 않는다.
- 응답에는 요일, 시작 시각, 종료 시각, 총 분이 포함된다.

## FR-AVAILABILITY-001 선호 만남 시간 설정

**설명**: 사용자는 공강 중 실제로 점심 메이트를 만날 시간을 정한다. 최소 만남 시간은 별도 매칭 선호 설정에서 관리한다.

**수용 기준**

- 월~금 11:00~15:00 범위에서 복수 구간을 설정할 수 있다.
- 같은 요일의 인접·중첩 선호 구간은 저장 시 병합한다.
- `유효 가능 시간 = 공강 ∩ 선호 시간`만 매칭에 사용한다.
- 공강과 겹치는 선호 시간이 없으면 저장은 가능하지만 추천 화면에서 수정 안내를 표시한다.
- 최소 만남 시간은 `FR-PREFERENCE-001`의 사용자 전체 설정을 사용한다.

## FR-MATCH-001 추천 후보 계산

**설명**: 시스템은 공통 점심 공강이 있는 동일 캠퍼스 사용자를 점수순으로 추천한다.

**후보 필터**

1. 동일 학교·캠퍼스이며 발견 허용 상태다.
2. 자신이 아니며 비활성 계정이 아니다.
3. 차단 기능이 구현된 경우 차단 관계가 아니다.
4. 공통 가능 시간이 존재한다.
5. 공통 가능 시간이 양쪽 최소 만남 시간 중 더 긴 값 이상이다.

**점수 규칙**

| 항목 | 점수 |
|---|---:|
| 가장 긴 공통 가능 시간 | 30분당 10점, 최대 60점 |
| `LUNCH` 활동 일치 | 20점 |
| 그 외 공통 활동 | 항목당 5점, 최대 15점 |
| 공통 관심사 | 항목당 3점, 최대 15점 |
| 언어교환 조건이 상호 일치 | 10점 |

**수용 기준**

- 총점 내림차순, 가장 긴 공통 시간, 공통 관심사 수, 사용자 ID 순으로 정렬해 결과가 안정적이어야 한다.
- 후보가 없을 때는 `선호 시간을 넓히거나 최소 만남 시간을 줄여보세요.`를 표시한다.
- 점수 계산에는 성별·국적 등 민감정보를 사용하지 않는다.
- 추천 응답에 상대의 수업명, 강의실, 전체 공강 목록은 포함하지 않는다.
- P0에서 실제 만남 제안 활동은 `LUNCH`만 제공한다. 언어교환·카페·운동 등 다른 활동은 대화 주제와 친밀도 판단을 위한 공통 태그로만 점수에 반영한다.

## FR-MATCH-002 추천 카드

**카드 표시 정보**

```text
닉네임 · 학년
같은 [캠퍼스]
공통 가능 시간 최대 3개
공통 활동과 관심사
추천 이유
[만남 제안] 버튼
```

**수용 기준**

- 추천 이유는 계산된 근거만 사용한다.
- 기본 템플릿: `월요일 12:00~13:30에 90분 동안 만날 수 있고, 두 분 모두 점심과 언어교환을 선호해요.`
- 생성형 AI를 사용해 문구를 다듬을 수 있으나, 후보 선정과 점수 계산은 서버 규칙으로만 수행한다.
- AI 호출 실패 시 템플릿 문구를 사용한다.

## FR-PLACE-001 공통 시간 기반 장소 추천

**설명**: 사용자가 만남 제안을 작성할 때, 시스템은 두 사람의 공통 시간과 선택한 활동에 맞는 캠퍼스 주변 장소를 추천한다.

**입력값**

- 캠퍼스 ID
- 제안 날짜·시각·총 만남 시간
- 활동 (`LUNCH` 우선)
- 선택: 예산대, 분위기

**장소 데이터 최소 필드**

| 필드 | 설명 |
|---|---|
| id, campusId, name | 장소 식별 및 캠퍼스 연결 |
| category | 식당/카페/스터디 공간 |
| walkMinutes | 캠퍼스 기준 도보 분 |
| priceRange | 예: 1만원 이하 |
| tags | 빠른 식사, 대화, 조용함 등 |
| description | 짧은 소개 |

**추천 규칙**

- `LUNCH`는 식당을 우선 추천한다.
- 만남 시간이 60분 이하이면 도보 5분 이내, `빠른 식사` 태그 장소를 우선한다.
- 만남 시간이 90분 이상이면 대화 가능 또는 여유 식사 태그를 가산한다.
- 예산·분위기 입력이 있으면 일치 장소를 우선한다.
- 조건을 통과한 장소를 최대 3개 반환한다.

**수용 기준**

- 장소명, 카테고리, 도보 시간, 가격대, 추천 이유를 표시한다.
- 장소 후보는 사전 등록 데이터에서만 선택한다. LLM은 새로운 장소를 생성할 수 없다.
- LLM은 선택된 장소에 대한 한 문장 추천 이유만 생성할 수 있다.
- 추천 실패 또는 후보 없음 시 `직접 입력`으로 제안을 계속할 수 있다.
- 실시간 영업 여부나 좌석 가능 여부를 보장한다는 문구를 표시하지 않는다.

## FR-PROPOSAL-001 만남 제안 생성

**설명**: 사용자는 추천 상대에게 특정 날짜·시간·활동·장소를 포함한 점심 만남을 제안한다.

**입력값**: 상대 사용자, 날짜, 시작·종료 시간, 활동, 장소(추천 장소 또는 직접 입력), 선택 메시지

**서버 검증**

1. 상대가 활성 상태이며 차단 관계가 아니다.
2. 날짜는 미래이고, 시작·종료는 30분 단위다.
3. 제안 날짜의 요일 기준으로 두 사용자의 공통 가능 시간 안에 전체 구간이 포함된다.
4. 두 사용자의 `ACCEPTED` 약속과 겹치지 않는다.
5. 동일한 두 사용자·날짜·시간의 `PENDING` 제안이 없다.
6. 발신자가 같은 만남 날짜에 다른 사용자에게 유지 중인 `PENDING` 또는 `ACCEPTED` 제안이 2명 미만이다.

**수용 기준**

- 장소는 추천 목록에서 하나를 고르거나 2~50자의 직접 입력값을 쓴다.
- 메시지는 선택이며 최대 200자다.
- 생성 직후 상태는 `PENDING`이다.
- 공통 가능 시간이 변경됐거나 확정 약속이 새로 생겼으면 최신 가능 시간을 보여주고 생성하지 않는다.
- 한 사용자는 **같은 만남 날짜 기준**으로 서로 다른 최대 2명에게만 `PENDING` 또는 `ACCEPTED` 제안을 유지할 수 있다.
- `REJECTED` 또는 `CANCELED` 상태 제안은 일일 2명 제한에 포함하지 않는다.
- 일일 제한에 도달하면 `해당 날짜에는 최대 2명에게만 만남을 제안할 수 있어요.`를 표시한다.

## FR-PROPOSAL-002 제안 수락·거절·취소

**설명**: 수신자는 대기 중 제안을 수락 또는 거절하며, 발신자는 수락 전 취소할 수 있다.

**상태 모델 — 단일 원본**

| 상태 | 의미 | 변경 권한 |
|---|---|---|
| `PENDING` | 수신자 응답 대기 | 수신자 수락/거절, 발신자 취소 |
| `ACCEPTED` | 확정 약속 | 양쪽 취소 |
| `REJECTED` | 수신자 거절 | 종료 |
| `CANCELED` | 발신자 또는 참여자 취소 | 종료 |

`ACCEPTED` 상태의 MeetingProposal을 약속 탭에서 조회한다. MVP에서는 별도 Appointment 테이블을 만들지 않는다.

**수용 기준**

- 수신자만 `PENDING → ACCEPTED/REJECTED`로 변경할 수 있다.
- 발신자만 `PENDING → CANCELED`로 변경할 수 있다.
- 수락 직전에 공통 가능 시간 및 양쪽 확정 약속 충돌을 다시 검증한다.
- 양쪽 참여자는 시작 시각 전까지 `ACCEPTED → CANCELED`로 변경할 수 있다.
- 상태가 바뀐 뒤 화면은 다음 조회 또는 폴링 시 최신 상태를 표시한다. 실시간 즉시 알림은 MVP 범위가 아니다.

## FR-PRIVACY-001 안전과 개인정보

**수용 기준**

- 다른 사용자에게는 공통 가능 시간만 보여주며, 개별 공강 목록·수업명·강의실을 반환하지 않는다.
- 이메일, 연락처, 인증 토큰은 어떤 카드·제안·약속 응답에도 포함하지 않는다.
- 사용자 입력 문자열은 출력 시 이스케이프 처리한다.
- 차단이 P1으로 미구현이면 데모 운영에서는 초대 사용자만 노출하고, 정식 서비스 전 차단 기능이 필요함을 명시한다.

### 장소 데이터 운영 기준

- MVP 장소 데이터는 팀이 데모 대상 캠퍼스 중심을 기준으로 직접 검수해 등록한다.
- `walkMinutes`는 캠퍼스 대표 기준점에서 산정한 추정치이며, 실시간 길찾기 결과가 아니다.
- 장소가 폐업·정보 변경된 경우 운영자가 `isActive=false`로 비활성화한다. MVP에서는 관리 화면 대신 시드 데이터 수정으로 처리할 수 있다.

## 5. API 초안

| 목적 | 메서드·경로 |
|---|---|
| 내 프로필 조회/저장 | `GET/PUT /me/profile` |

| 수업 조회/등록 | `GET/POST /me/schedules` |
| 수업 수정/삭제 | `PATCH/DELETE /me/schedules/:id` |
| 선호 시간 조회/저장 | `GET/PUT /me/availability` |

## 6. 데모 시나리오

### 준비 데이터

- 사용자 A: 같은 캠퍼스, 월요일 12:00~14:00 유효 가능 시간, 점심·언어교환 선호
- 사용자 B: 같은 캠퍼스, 월요일 12:00~13:30 유효 가능 시간, 점심·언어교환 선호
- 사용자 C: 다른 캠퍼스 또는 공통 가능 시간이 없음
- 장소: 학생회관 식당(도보 3분, 빠른 식사), 캠퍼스 앞 덮밥집(도보 6분), 카페(도보 4분)

### 흐름

1. 사용자 A로 로그인해 시간표와 월요일 공강을 확인한다.
2. 월요일 12:00~14:00, 최소 60분을 선호 시간으로 설정한다.
3. 사용자 B 카드에서 `월요일 12:00~13:30` 공통 가능 시간과 추천 이유를 확인한다.
4. `만남 제안`에서 월요일 12:00~13:00 점심을 선택한다.
5. AI 장소 추천에서 `학생회관 식당 · 도보 3분 · 빠른 식사`를 선택한다.
6. 사용자 B로 전환해 제안을 수락한다.
7. 양쪽 약속 탭에서 같은 날짜·시간·장소의 `ACCEPTED` 약속을 확인한다.

### 데모 합격 기준

- B는 추천되고 C는 추천되지 않는다.
- 60분 공강에는 가까운 빠른 식사 장소가 우선 추천된다.
- AI/장소 추천이 실패해도 직접 장소 입력으로 제안을 보낼 수 있다.
- 상대의 전체 시간표·과목명·강의실은 어느 화면에도 노출되지 않는다.
- 동일 시간의 두 번째 확정 약속은 생성·수락되지 않는다.

## 7. 최종 체크리스트

- [ ] 프로필, 시간표, 선호 시간을 설정할 수 있다.
- [ ] 11:00~15:00 공강과 유효 가능 시간이 올바르게 계산된다.
- [ ] 동일 캠퍼스·공통 가능 시간·최소 만남 시간을 만족하는 사용자만 추천된다.
- [ ] 추천 이유가 계산된 사실과 일치한다.
- [ ] 제안 화면에서 공통 시간에 맞는 장소 최대 3개를 추천한다.
- [ ] 추천 장소를 선택하거나 직접 입력해 제안을 보낼 수 있다.
- [ ] 같은 만남 날짜에 한 사용자가 유지할 수 있는 대기·확정 제안은 서로 다른 최대 2명이다.
- [ ] 수락 시 시간표와 기존 확정 약속의 충돌을 다시 검사한다.
- [ ] 수락된 제안이 양쪽 약속 화면에 같은 정보로 표시된다.
- [ ] 상대의 수업 상세와 연락처가 노출되지 않는다.
- [ ] AI·장소 추천이 실패해도 매칭과 제안 핵심 경로가 동작한다.
