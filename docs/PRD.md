# 공강 기반 AI 점심 메이트 서비스 PRD

> 문서 버전: v0.2
> 작성 기준: 2026-08-16 KST
> 제출 마감: 2026-08-16 17:30 KST
> 핵심 카피: **시간표의 빈칸을, 새로운 만남과 맛있는 한 끼로 채워보세요.**

## 1. 제품 요약

대학생의 주간 시간표에서 점심 공강을 계산하고, 같은 캠퍼스에서 공통 시간이 겹치는 점심 메이트를 추천한다. 사용자가 상대에게 만남을 제안할 때 공통 시간, 캠퍼스, 활동, 예산을 바탕으로 실제 후보 데이터 안에서 주변 장소 3개를 추천한다.

서비스의 차별점은 다음 두 정보를 하나의 결정 흐름으로 연결하는 것이다.

```text
누구와 만날 수 있는가?
→ 공통 공강 기반 점심 메이트 추천

짧은 공강 안에 어디에서 만날 수 있는가?
→ 캠퍼스 주변 장소와 추천 이유 제공
```

AI는 사람이나 장소를 임의로 창작하지 않는다. 매칭 후보와 장소 후보는 서버 데이터와 규칙으로 결정하고, AI는 이미 계산된 사실을 자연어 추천 이유로 설명하는 데만 사용한다.

## 2. 문제 정의

대학생은 수업 사이 시간이 비어 있어도 다음 문제 때문에 새로운 사람과 점심 약속을 잡기 어렵다.

- 누가 같은 시간에 비는지 알기 어렵다.
- 시간표상 공강과 실제로 만나고 싶은 시간이 다르다.
- 공강이 짧으면 이동 거리와 식사 시간을 고려해 장소를 고르기 어렵다.
- 전체 시간표나 연락처를 공개하는 것은 부담스럽다.
- 유학생과 교환학생은 같은 캠퍼스 안에서도 자연스럽게 만날 계기가 부족하다.

## 3. 목표와 비목표

### 3.1 해커톤 목표

사용자가 다음 데모 경로를 중단 없이 완료할 수 있어야 한다.

```text
데모 계정 로그인
→ 프로필 확인
→ 점심 시간표 입력
→ 공강·선호 시간 설정
→ 메이트 추천
→ 장소 3개 추천
→ 제안 생성
→ 상대 계정에서 수락
→ 수락된 제안을 약속 탭에서 확인
```

### 3.2 비목표

- 전체 대학과 캠퍼스 데이터 구축
- 실시간 영업시간·혼잡도·웨이팅 보장
- 학교 포털 연동 또는 크롤링
- LLM이 실제 장소나 사용자 후보 생성
- 그룹 매칭, 채팅, 알림, 결제
- 공휴일·휴강·보강 일정 연동
- 정교한 머신러닝 추천 모델

## 4. 사용자와 핵심 가치

### 4.1 주요 사용자

- 같은 캠퍼스에서 점심 친구를 찾는 대학 재학생
- 한국 학생과 자연스럽게 만나고 싶은 유학생·교환학생
- 짧은 공강 안에 갈 수 있는 장소를 빠르게 정하고 싶은 학생

### 4.2 가치 제안

| 사용자 문제 | 제품 가치 |
|---|---|
| 서로의 빈 시간을 모름 | 시간표에서 공통 가능 시간을 자동 계산 |
| 전체 시간표 공개가 부담됨 | 공통 가능 구간만 공개 |
| 장소 결정에 시간이 걸림 | 공강 길이와 캠퍼스 거리를 반영한 장소 3개 추천 |
| 추천 근거를 신뢰하기 어려움 | 점수와 같은 데이터로 추천 이유 설명 |
| AI 오류가 데모를 막을 수 있음 | 규칙 기반 결과와 템플릿 폴백 제공 |

## 5. 제품 원칙

1. **알고리즘이 결정하고 AI가 설명한다.** 공강, 사용자 후보, 장소 후보는 결정론적 로직으로 계산한다.
2. **공통 정보만 공개한다.** 상대의 전체 시간표, 수업명, 강의실, 이메일과 연락처를 공개하지 않는다.
3. **장소는 검증된 후보에서만 고른다.** LLM이 장소명, 거리, 가격, 영업 정보를 생성하지 않는다.
4. **핵심 경로에는 폴백이 있다.** AI·OCR·장소 추천이 실패해도 수동 입력으로 제안할 수 있다.
5. **오늘 구현할 것만 P0다.** 데모에 보이지 않는 계정·관리 기능은 P1 이후로 미룬다.

## 6. MVP 정책

### 6.1 서비스 범위

| 항목 | MVP 정책 |
|---|---|
| 캠퍼스 | 연세대학교 신촌캠퍼스 1곳 |
| 서비스 시간 | 평일 11:00~15:00 |
| 시간 단위 | 30분 |
| 최소 만남 시간 | 기본 60분, 30·60·90·120분 선택 |
| 시간표 | 한 학기 동안 반복되는 월~금 주간 규칙 |
| 공휴일·휴강 | 반영하지 않고 주간 규칙을 그대로 적용 |
| 장소 데이터 | 검증된 더미 식당·카페 6~10개 |
| 장소 추천 수 | 최대 3개 |
| 사용자 데이터 | 사전 생성된 데모 계정 2~3개 |

### 6.2 학생 신뢰 정책

MVP는 공개 가입 서비스가 아니다. 팀이 만든 초대·데모 계정과 사전 등록한 학교·캠퍼스 데이터만 사용한다. 이 계정은 `DEMO_VERIFIED` 상태로 표시한다.

정식 서비스에서는 학교 이메일 인증을 추가한다.

```text
DEMO_VERIFIED
- 해커톤 사전 생성 계정
- MVP 매칭 가능

SCHOOL_EMAIL_VERIFIED
- 허용 학교 도메인 이메일 인증 완료
- 정식 서비스 매칭 가능

UNVERIFIED
- 인증 전 계정
- 프로필 편집은 가능하지만 매칭·제안 불가
```

`@yonsei.ac.kr` 등 실제 허용 도메인은 학교 데이터에 설정한다. 공개 회원가입과 인증 메일 발송은 P1이다.

### 6.3 인증 정책

- 자체 이메일·비밀번호 로그인 방식을 유지한다.
- P0는 사전 생성된 데모 계정 로그인과 내 정보 조회만 구현한다.
- 회원가입 UI, Refresh Token 갱신, 비밀번호 재설정은 P1이다.
- 데모 계정 비밀번호도 원문으로 저장하지 않고 해시로 저장한다.
- P0 Access Token 만료 시간은 데모 세션을 고려해 최대 4시간으로 제한한다.

## 7. P0/P1/P2 범위

### P0 — 데모 필수

1. 데모 계정 로그인과 내 정보 조회
2. 최소 프로필 조회·저장
3. 주간 수업 전체 저장과 공강 계산
4. 선호 시간과 최소 만남 시간 저장
5. 규칙 기반 메이트 추천 카드
6. 최소 차단 생성과 매칭 제외
7. 검증된 데이터 기반 장소 3개 추천
8. 만남 제안 생성과 받은 제안 수락
9. 수락된 제안을 약속 탭에서 조회
10. AI 실패 시 템플릿 추천 이유

### P1 — 핵심 경로 안정화 후

- 공개 회원가입, Refresh Token, 로그아웃 API
- 학교 이메일 인증
- 프로필 세부 수정, 이미지, 자기소개, 언어교환
- 개별 수업 CRUD
- 제안 거절·취소, 차단 목록·해제, 신고
- 관심 표시·넘기기
- 실제 장소 API 연동과 장소 데이터 관리

### P2 — 확장

- 시간표 OCR
- 공휴일·휴강·보강 예외 일정
- 실시간 영업시간·웨이팅
- 채팅·알림·그룹 매칭
- 여러 학교와 학교 간 매칭

## 8. 핵심 기능 요구사항

### FR-AUTH-001 데모 계정 로그인 `[P0]`

사전 생성된 이메일과 비밀번호로 로그인한다. 로그인 성공 시 Access Token과 사용자·프로필 상태를 반환한다.

수용 기준:

- 올바른 데모 계정으로 로그인할 수 있다.
- 비밀번호 원문을 저장하거나 로그에 남기지 않는다.
- `DEMO_VERIFIED` 또는 `SCHOOL_EMAIL_VERIFIED` 사용자만 매칭·제안을 이용할 수 있다.
- 잘못된 이메일과 비밀번호에는 같은 실패 메시지를 사용한다.

### FR-PROFILE-001 최소 프로필 설정 `[P0]`

학교, 캠퍼스, 학년, 닉네임, 활동과 관심사를 저장한다. 학과와 학생 유형은 내부 프로필에는 저장할 수 있지만 추천 카드에는 기본 공개하지 않는다.

추천 카드 공개 정보:

```text
닉네임
같은 신촌캠퍼스 · 학년
공통 가능 시간
공통 활동과 관심사
추천 이유
```

금지 정보:

- 이메일과 연락처
- 수업명과 강의실
- 전체 시간표와 개별 선호 시간
- 학과, 학생 유형, 자기소개 기본 공개

### FR-SCHEDULE-001 주간 수업 전체 저장 `[P0]`

사용자는 월~금의 수업 목록을 한 번에 저장한다. 서버는 기존 목록을 전체 교체하고 수업 간 중복을 검증한다. 개별 수업 생성·수정·삭제 API는 P1이다.

### FR-SCHEDULE-002 공강 자동 계산 `[P0]`

서버는 평일 11:00~15:00에서 수업 구간을 제외해 30분 이상의 공강을 계산한다. 수업 종료와 공강 시작의 같은 경계는 충돌하지 않는다.

### FR-AVAILABILITY-001 선호 시간 설정 `[P0]`

사용자는 실제로 만날 요일·시간과 최소 만남 시간을 설정한다. 매칭에는 공강과 선호 시간의 교집합만 사용한다.

### FR-MATCH-001 메이트 추천 `[P0]`

동일 학교·캠퍼스의 인증 사용자 중 공통 가능 시간이 양쪽 최소 만남 시간을 충족하는 사용자를 추천한다.

제외 대상:

- 자기 자신
- 다른 학교·캠퍼스 사용자
- `UNVERIFIED` 사용자
- 공통 가능 시간이 부족한 사용자
- 차단 관계 사용자
- 탈퇴·이용 제한 사용자

매칭 순위는 공통 시간, 활동, 관심사, 언어 조건의 설명 가능한 점수로 정한다.

### FR-BLOCK-001 최소 사용자 차단 `[P0]`

사용자는 추천 카드에서 상대를 차단할 수 있다. P0는 차단 생성과 매칭 제외만 구현하고 차단 목록·해제 UI는 P1로 미룬다.

수용 기준:

- 차단 즉시 양쪽 사용자가 서로의 추천에서 제외된다.
- 신규 만남 제안을 생성할 수 없다.
- 차단 사실을 상대에게 알리지 않는다.
- 자기 자신과 동일 대상을 중복 차단할 수 없다.

### FR-PLACE-001 공통 시간 기반 장소 추천 `[P0]`

사용자가 만남을 제안할 때 시스템은 선택한 캠퍼스, 날짜·시간, 활동과 선택 조건을 기준으로 주변 장소를 최대 3개 추천한다.

입력:

- 캠퍼스
- 만남 날짜, 시작·종료 시간
- 활동: 점심, 카페, 스터디 등
- 선택 예산: 저가, 보통, 여유
- 선택 분위기: 빠른 식사, 조용함, 대화하기 좋음

출력:

- 장소 ID와 장소명
- 카테고리
- 캠퍼스 기준 도보 거리와 예상 소요 시간
- 가격대
- 추천 이유
- 장소 선택 가능 여부

수용 기준:

- 점심 활동이면 식당을 우선 추천한다.
- 만남 시간이 60분 이하이면 도보 시간이 짧고 빠른 식사가 가능한 장소를 우선한다.
- 추천 장소는 최대 3개만 반환한다.
- 장소 후보는 검증된 데이터 6~10개 안에서만 선택한다.
- 사용자는 추천 장소를 선택하거나 장소명을 직접 입력할 수 있다.
- 장소 추천 실패 시에도 수동 입력으로 제안을 완료할 수 있다.
- LLM은 장소를 선택하거나 속성을 생성하지 않고 추천 이유 문장만 생성한다.
- AI 실패 시 서버 템플릿 문구를 사용한다.

장소 점수 v1:

| 항목 | 점수 |
|---|---:|
| 활동 카테고리 일치 | 40점 |
| 예산 일치 | 20점 |
| 분위기 일치 | 15점 |
| 도보 5분 이하 | 20점 |
| 도보 10분 이하 | 10점 |
| 60분 이하 만남에서 빠른 식사 가능 | 20점 |

### FR-PROPOSAL-001 날짜 기반 만남 제안 `[P0]`

사용자는 추천 상대에게 특정 날짜·시간, 활동과 장소를 포함한 제안을 보낸다.

생성 시 검증:

1. 제안 날짜의 요일이 두 사용자의 주간 공통 가능 요일과 같아야 한다.
2. 제안 시간 전체가 최신 공통 가능 구간 안에 포함되어야 한다.
3. 두 사용자 모두 같은 날짜의 `ACCEPTED` 제안과 시간이 겹치지 않아야 한다.
4. 제안 시각은 미래이며 다음 28일 이내여야 한다.
5. 추천 장소를 선택하거나 직접 장소명을 입력해야 한다.

MVP는 공휴일·휴강을 별도로 판단하지 않고 주간 시간표 규칙을 적용한다.

### FR-PROPOSAL-002 제안 수락 `[P0]`

수신자는 `PENDING` 제안을 수락할 수 있다. 서버는 수락 순간 공통 가능 시간과 두 사용자의 확정 제안 충돌을 다시 검사한다.

수용 기준:

- 수신자만 수락할 수 있다.
- 제안 시작 시각이 지났으면 수락할 수 없고 시스템이 `CANCELED`로 전환한다.
- 시간표·선호 시간이 변경돼 공통 시간이 사라지면 수락하지 않는다.
- 확정 약속과 겹치면 수락하지 않는다.
- 동시에 수락해도 한 번만 성공한다.

### FR-PROPOSAL-003 단일 제안·약속 상태 모델 `[P0]`

MVP는 별도 Appointment 엔티티를 만들지 않는다. `MeetingProposal`이 상태의 단일 원본이다.

```text
MeetingProposal
- PENDING: 응답 대기
- ACCEPTED: 수락 완료, 약속 탭에 표시
- REJECTED: 수신자 거절
- CANCELED: 발신자·참여자·시스템 취소
```

- 제안 수락 시 별도 Appointment 레코드를 생성하지 않는다.
- 약속 탭은 `ACCEPTED` 제안을 날짜순으로 조회한다.
- `PENDING`은 발신자만 취소할 수 있고, `ACCEPTED`는 양쪽 참여자가 취소할 수 있다.
- 시작 시각이 지난 `PENDING` 제안은 `CANCELED`로 전환하고 취소 원인을 `TIME_EXPIRED`로 기록한다.

## 11. 핵심 비즈니스 규칙

### 시간 구간 겹침

두 구간 `[startA, endA)`, `[startB, endB)`는 다음 조건이면 겹친다.

```text
startA < endB AND startB < endA
```

따라서 `12:00~13:00`과 `13:00~14:00`은 겹치지 않는다.

### 확정 제안 충돌

제안 생성과 수락 시 두 사용자 각각에 대해 같은 날짜의 `ACCEPTED` 제안과 겹치는지 검사한다. `PENDING`, `REJECTED`, `CANCELED`는 확정 충돌 대상이 아니다.

### 개인정보 공개

| 단계 | 공개 정보 |
|---|---|
| 추천 카드 | 닉네임, 캠퍼스, 학년, 공통 시간·활동·관심사, 추천 이유 |
| 제안 | 위 정보 + 제안 날짜·시간·장소·메시지 |
| 수락 후 | 제안 정보와 상태. 이메일·연락처·전체 시간표는 계속 비공개 |

## 12. AI 사용 정책

### 허용

- 계산된 매칭 근거를 자연어 추천 이유로 변환
- 선택된 장소와 점수 근거를 자연어 추천 이유로 변환

### 금지

- 존재하지 않는 사용자·장소 생성
- 장소명·거리·가격·영업시간 추측
- 공강 계산과 충돌 검증
- AI 점수만으로 후보 추가·제외

### 폴백

```text
매칭: 월요일 12:00~13:30에 공강이 겹치고 두 분 모두 점심을 선호해요.

장소: 공강이 60분이라 캠퍼스에서 도보 3분 거리의 빠른 식사 장소를 추천해요.
```

## 13. 데모 시나리오

### 준비 데이터

- 사용자 A: 월요일 12:00~14:00, 점심 선호
- 사용자 B: 월요일 12:00~13:30, 점심 선호
- 사용자 C: 다른 캠퍼스 또는 공통 시간 없음
- 장소: 신촌 캠퍼스 검증 데이터 6~10개
- 사용자 A와 B: `DEMO_VERIFIED`

### 메인 데모

1. 사용자 A로 로그인한다.
2. 월요일 12:00~14:00 공강을 확인한다.
3. 사용자 B 추천 카드에서 공통 시간과 이유를 확인한다.
4. 월요일 12:00~13:00을 선택한다.
5. 시스템이 가까운 점심 장소 3개와 추천 이유를 표시한다.
6. 장소 하나를 선택해 제안을 보낸다.
7. 사용자 B로 로그인해 제안을 수락한다.
8. `ACCEPTED` 제안이 양쪽 약속 탭에 표시된다.

### 반드시 보여줄 차별점

> 공강이 60분이라 캠퍼스에서 도보 3분 거리이고 빠르게 식사할 수 있는 장소를 추천해요.

### 실패 복구 데모

- AI를 끄면 템플릿 추천 이유가 표시된다.
- 장소 추천 API가 실패하면 직접 장소 입력으로 제안을 완료한다.
- 같은 시간에 확정 제안이 있으면 중복 수락이 거부된다.

## 14. 성공 기준

- 데모 계정 로그인부터 수락된 약속 조회까지 3분 안에 완료한다.
- 추천 결과에 상대의 전체 시간표가 노출되지 않는다.
- 장소 추천은 검증된 후보에서 최대 3개만 반환한다.
- 장소 추천 실패 시 수동 장소로 제안할 수 있다.
- 두 사용자의 확정 제안이 같은 시간에 중복 생성되지 않는다.
- AI를 끈 상태에서도 핵심 경로가 동작한다.
